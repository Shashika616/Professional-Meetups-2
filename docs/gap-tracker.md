## Round 2 — full architecture/optimization sweep (2026-09-08)

Dispatched two independent, from-scratch reviews (backend, frontend) explicitly told to skip everything already listed above and find new territory only. One finding (#17) is a genuine correctness bug, verified directly against source, not just accepted from the report.

### Backend

17. **Trust-level lost-update race across independent verification steps — real correctness bug, verified.** `backend/internal/modules/auth/verification.go`'s `VerifyPhoneCode` (67-87), `VerifyPersonalEmailCode` (105-125), and `SubmitPersonalDetails` (130-154) each do read-then-compute-then-write with no transaction spanning the two and no lock: fetch the user row, build a Go-side "hypothetical" copy with only *this* field added, compute `trust_level` from that snapshot, then `UPDATE` the real field plus that precomputed `trust_level`. If two of a user's Level-2 steps complete inside the same short window (very plausible — a user clicking through the verification checklist quickly), each computes trust level from a snapshot that can't see the other's not-yet-committed field. Both underlying fields end up correctly persisted, but `trust_level` gets stamped by whichever write commits last, computed as if only its own field existed — silently under-granting the user's trust level, with nothing to ever recompute it afterward. This is the exact bug class already found and fixed for the meetups-completed cache (`queries/users.sql:135-151`, value-guard not timestamp-guard) — that fix was never generalized to these three `UpdateUser*` call sites, which have no guard at all. On closer design pass, the identical shape (precomputed `trustLevel int`, no lock) also exists in `UpdateWorkEmailVerified`, `UpdateLinkedInSub`, and `ClearGuestFlag` — same bug, three more call sites. **Fix designed and handed off 2026-09-08: `docs/plans/12-trust-level-race-fix.md` + `docs/plans/12-trust-level-race-fix-claude-code-prompt.md`.** Chosen fix is a `SELECT ... FOR UPDATE` row lock inside a transaction (matching the existing `refresh_tokens_postgres.go` `Rotate` idiom) with `trust_level` recomputed from the locked row via a callback, not a SQL-side `CASE` — keeps `computeTrustLevel`'s logic in exactly one place (Go), not duplicated into SQL. Covers all six affected methods in one pass. **DONE (2026-09-09) — verified against actual source, not just the completion report.** Confirmed directly: all six repository methods now lock via a new `GetUserByIDForUpdate` (`SELECT ... FOR UPDATE`) inside a transaction, apply their own field(s) to the locked snapshot, invoke the caller's callback, write and commit before publishing. All seven service-layer call sites (four in `verification.go`, three in `identity_resolution.go` — including `SignUpOrRecoverWithEmail`'s `UpdatePersonalEmail` call, which neither plan document named but was caught by treating the compiler as authoritative) pass the matching closure. Six fakes rewritten to mutate their own row before invoking the callback, so existing tests exercise real logic, not just a recompiled signature. Three predicted literal-argument test breaks (`identity_resolution_test.go:268,291`, `service_test.go:543`) fixed as predicted. New `trustlevel_race_test.go` (4 tests) reproduces the exact bug shape and passes; a control run confirmed it fails on the old code (`stored trust_level = 1, want 2`). `go build ./...` and `go test ./...` both pass. Honestly-stated limit: a fake repository can't prove the real Postgres row lock serializes concurrent transactions — only a live integration test could — and the report didn't overclaim this.

18. **Missing regression test plus a stale "this is tested" comment on the rating/meetups-completed cache consumers.** `backend/internal/modules/auth/rating_consumer.go:33,55` (`ApplyRatingUpdate`, `ApplyMeetupsCompletedUpdate`) have zero calling test anywhere in the repo. `fakes_test.go:262-264`'s own comment claims a test "exercise[s] this directly" — it doesn't exist. The underlying guard was itself corrected same-day (`fakes_test.go:285-290`) with no regression test added to lock the fix in, on exactly the redelivery/out-of-order-event logic ADR-001 calls "real insurance against a handler running twice." **OPEN.**

19. **`ListActiveMeetups` fetches full pages (up to 400 rows, joined) before filtering down to the handful actually shown.** `backend/internal/modules/meetup/service.go:461-469` calls `ListByHost`/`ListRequestedByUser` with the default 200-row page size each, joined against host-display + rating-average, then discards most of it in Go down to just `open`/`full`/unexpired rows. Pushing that filter into SQL would avoid the wasted transfer/join on every pull-to-refresh and app-resume. Low severity (polling was deliberately removed already) but real waste for any host/participant with meetup history. **OPEN — low priority.**

## Round 3 — full design review, bad-design/architecture lens (2026-09-09)

Two independent from-scratch reviews (backend, frontend), each given the full list of everything already logged above (#1-24) and told to find new territory only, explicitly asked for design smells and architectural issues, not just bugs. I personally re-verified the four most consequential findings directly against source before recording them (#25, #27, #28, #29 below) rather than relaying the reports as-is; #26 is recorded as reported, not independently re-checked line-by-line.

### Backend

25. **`ListRatableParticipants` doesn't apply the same identity-redaction floor `ListMeetupParticipants` deliberately enforces — verified.** `backend/internal/modules/meetup/participants.go:68-100`'s `ListMeetupParticipants` redacts `UserID`/`FullName`/`ProfilePhotoURL`/`TrustLevel` for any viewer below `participantIdentityFloor` (trust level 2), with an explicit, carefully-written rationale: "somebody who cannot join has no reason to need the guest list, and letting them read it would make the app a directory that anyone can scrape by signing up" (`participants.go:7-20`). `ListRatableParticipants` (`rating.go:22-41`) answers the same underlying question — who's on this meetup — for the same viewer/meetup pair, but returns full identities gated only by `IsParticipant`, with no trust-level check and no `RatableParticipant` field to redact against. Confirmed this is reachable, not theoretical: joining a meetup required only trust level 1 before ADR-013 raised the floor to 2, so a participant who joined under the old floor is a legitimate, still-current participant sitting below `participantIdentityFloor` today — exactly the "grandfathered participant" case `GetMeetup`'s own comment (`service.go:359-365`) already accounts for elsewhere. That participant sees full names/photos/trust levels of everyone else on the meetup via `ListRatableParticipants`, on a meetup where `ListMeetupParticipants` would redact them to a bare count. Not a general scraping hole (the `IsParticipant` gate is real and load-bearing, per the method's own comment) — it's a policy the codebase enforces carefully in one place and forgot to apply in a second, structurally identical place. **DONE (2026-09-09) — verified against actual source.** Confirmed the full chain: `meetup.proto`'s `viewer_trust_level` field, regenerated stubs, both `monolithclient` layers, `handlers/meetups.go` sourcing it from the JWT, and `rating.go` zeroing `TrustLevel` on the post-`ratableParticipantsFromRepo` slice (the corrected location) with a clear doc comment on the deliberate partial redaction. New `TestListRatableParticipants_RedactsOnlyTrustLevel_Integration` runs against a real test database (not a fake) and proves both directions: trust level zeroed below the floor while name/ID survive, real value returned at the floor. `go build`/`go test` both pass.

26. **N+1 sequential per-meetup queries inside the lifecycle-sweep's row-locked claim transaction — reported, not independently re-verified line-by-line.** `NotifyStartingSoonSweep` and `AutoCloseSweep`/`queueMeetupClosed` (`service.go:653-680`, `616-642`, `687-704`) loop over up to 100 claimed meetups and call `ListRequestsForMeetup` once per meetup, synchronously, inside the same `SELECT ... FOR UPDATE SKIP LOCKED` transaction that claims them (`meetups_postgres.go:821-875`) — no batched `ListRequestsForMeetups([]ID)` exists. The codebase already found and fixed this exact shape of problem once, for `recomputeMeetupsCompleted` (`meetups_postgres.go:663-683`, moved out of the closing transaction specifically because it scaled with participants × history while holding locks on `meetup.meetups`) — that fix was never generalized here. Extends lock hold time and DB round-trips proportionally to sweep batch size, on a poller that runs every 60s. **OPEN — worth a follow-up read before prioritizing, given the source review's strong track record of getting this codebase's reasoning right elsewhere.**

### Frontend

27. **DONE (2026-09-09) — verified against actual source.** `setState` after dispose in the Add Trusted Contact dialog's error path — real bug, one missing `mounted` check. `if (!mounted) return;` confirmed in place with an explanatory comment. `frontend/lib/features/safety/manage_trusted_contacts_page.dart:328-347`'s `_save()`: the `on AuthException catch (error)` block calls `setState(() => _error = ...)` with no `mounted` guard, while the `finally` block three lines below correctly guards its own `setState` with `if (mounted)`. If the dialog is dismissed while `addTrustedContact` is in flight and it then throws, this asserts/crashes in debug and is undefined behavior in release. Every other async handler in the codebase (`meetup_detail_page.dart`, `host_meetup_controls.dart`, `schedule_flow.dart`) consistently guards every post-await `setState`; this is the one place that pattern was dropped. **OPEN.**

28. **`MeetupSessionExpiredException` is thrown on every meetup-API 401 but never caught anywhere — verified, confirmed via direct grep and read of `app_shell.dart`.** `core/services/http_meetup_service.dart:344` throws it, and its own doc comment (`meetup_service.dart:247-252`) says it means exactly what `AuthService.SessionExpiredException` means. But a repo-wide search for the type turns up only its definition and that one throw site — zero catch sites. Every meetup call site (`meetup_detail_page.dart`, `schedule_flow.dart`, `host_meetup_controls.dart`, `happening_soon_section.dart`, `events_page.dart`, `share_with_contacts_sheet.dart`) catches only the generic `MeetupException` and shows a toast. Contrast with `AuthService.SessionExpiredException`, which five call sites explicitly catch to call `forceSignOut()`. `AppShell`'s own safety-net listener (`app_shell.dart:194-217`) exists specifically for "any authenticated call site that forgot its own `SessionExpiredException` catch" — but it only fires when `authSessionProvider` actually transitions to logged-out, which nothing does for the meetup-service variant. Net effect: a session that dies mid-use of any meetup feature shows a generic, retriable-looking error forever with no path back to sign-in. Related but distinct, and corrected from the original report: the Safety Center's SOS confirm dialog (`safety_page.dart:203-234`) calls `AuthService.triggerSos` (not the meetup service), and its `on AuthException catch` is broad enough to also swallow a `SessionExpiredException` without calling `forceSignOut()` — same failure *pattern* (generic catch, no forced sign-out), but a separate instance on the auth service's own exception, not the same bug as the meetup-service gap. **DONE (2026-09-09) — verified against actual source.** Fixed at 21 sites across 10 files, four more than either plan document named (`participants_page.dart`, `meetup_review_page.dart`, `meetup_review_section.dart`, `participants_strip.dart`) — caught by the implementer's own grep rather than trusting the plan's list, exactly the discipline the plan asked for. Spot-checked several sites directly, including the three `catch (_)` best-effort-load sites: all correctly special-case `MeetupSessionExpiredException` before the generic handler. SOS dialog fix confirmed correctly ordered (`on SessionExpiredException` before `on AuthException catch`). `share_with_contacts_sheet.dart` was correctly dropped from the list — confirmed it doesn't call the meetup service at all.

29. **`ScheduleFlowPage`'s step-back logic only runs on its custom in-app back button — the OS back gesture bypasses it and discards the whole wizard, verified.** `schedule_flow.dart:194-227`'s `_Header` is a plain `Row` (the `Scaffold` has no `appBar:`), and `_goBack()`'s deliberate one-step-back logic is wired only to that `IconButton`'s `onPressed`. Real, easily-triggered data-loss path on a form with actual backend consequences. **DONE (2026-09-09) — verified against actual source.** `PopScope<void>` confirmed wrapping the `Scaffold`, routed through the existing `_goBack()`. Plan guessed the wrong callback name (`onPopInvokedWithPopScope`, which doesn't exist); implementer correctly used `onPopInvokedWithResult`, the real non-deprecated API for the installed Flutter SDK (3.47.0) — checked the SDK source rather than guessing, as instructed.

## Round 4 — guest-account lifecycle review (2026-09-09)

Surfaced from a user question about what happens to a guest account after
sign-out, not from a scheduled sweep — same reactive pattern the Process
Note below already calls out.

30. **`AddTrustedContact`/`TriggerSOS` have no trust-level gate — any guest (Level 0, never verified) can use both.** Checked directly: both gateway routes require only `h.requireAuth`. Built (ADR-026, in the vault) before the guest/trust-level-0-3 redesign existed, so this isn't a reversed decision — trust level was never considered for these two RPCs at all. Real consequence found while designing guest-account cleanup: `auth.trusted_contacts`/`auth.sos_events` were deliberately built with no real FK to `auth.users` (migration 0001, for module re-extractability), so deleting an abandoned guest that had used either would leave silently orphaned rows behind. **DONE (2026-09-09) — verified directly against source, not just the completion report.** `safetygate.go`'s `requireSafetyFeatureTrustLevel` (floor 2) is called at the top of both `service.go` methods; the full proto→gateway→grpcapi→service chain threading `caller_trust_level` from the JWT (never client-supplied) confirmed end to end. Three new backend tests confirmed genuinely adversarial, not just compiling around the change: sub-floor calls rejected with zero `sos_events` written, the gate runs *before* input validation (so a rejected caller learns nothing about the layer behind it), and floor-and-above succeeds. Frontend `safety_page.dart` gates `_onSosTapped` and the add-contact entry point via `ref.watch(authSessionProvider)` (a bug in an earlier pass used `ref.read` at tap time, which raced `AsyncLoading` to a false "guest" read — caught by the existing widget tests, now fixed).

31. **No cleanup mechanism for abandoned guest accounts — rows accumulate in `auth.users` forever.** A guest account has no credential to re-authenticate with once its refresh token is gone (logout revokes and deletes it locally; nothing else identifies the account), so "Continue as Guest" always creates a fresh account rather than resuming an old one. Checked all six background jobs in `cmd/monolith/main.go` — none touch `auth.users`. Mitigated somewhat by the existing 5/IP/day guest-signup rate limit, but that's IP-keyed (defeated by a proxy pool) and doesn't address ordinary abandonment (reinstalls, uninstalls, one-time tries). **DONE (2026-09-09) — verified directly against source.** `RefreshTokenSweeper.Tick` now runs `SweepAbandonedGuests` right after the token sweep (order confirmed load-bearing and documented: guest eligibility requires zero token rows, so cleanup must run second). New repository method `DeleteAbandonedGuests` confirmed batched like `DeleteExpired`, with three required conditions read directly from the SQL: `is_guest = true` (a hard, one-way exclusion — verified nothing ever flips it back), a real anti-join against `auth.refresh_tokens` (not a derivable stored flag), and `updated_at` past the same `RefreshTokenRetention` window the token sweep already uses. Only safe in this simplified two-condition-plus-retention form because #30 landed first, per ADR-003's Consequences — confirmed that ordering was actually followed. **New gap surfaced during this verification, not yet fixed — see #32.**

32. **Deleting a guest account (new as of #31's fix) can orphan rows in three `meetup` schema tables that also have no FK to `auth.users` by the same deliberate module-boundary design (migration 0002's header, mirroring 0001's).** Verified directly: `meetup.user_display_cache` gets a row for every account via the `user-onboarded` event (`users_postgres.go`'s `Create`, which `GuestSignup` calls, publishes it unconditionally) — so literally every guest has one. `meetup.user_location_cache` (`POST /v1/users/me/location`) and `meetup.device_tokens` (`POST /v1/meetups/device-token`) are both `h.requireAuth`-only routes, reachable by a Level-0 guest with no trust check at all — confirmed both route registrations directly. #30/#31 do NOT close this: #30 only gates the two `auth`-module safety writes, and #31's cleanup deletes the `auth.users` row itself, not these three `meetup`-module rows, which would be left behind pointing at a UUID that no longer exists anywhere. Self-flagged by the implementer rather than found independently, and confirmed real on inspection. Correct fix is a `user-deleted` event the `meetup` module consumes to clean up its own three tables — an ADR-001 module-boundary matter, not a one-line patch, so it wasn't slipped into Part B's scope. **OPEN — not yet designed.**

## Round 5 - live traffic review of the deployed service (2026-09-10)

Both items below were found by reading the deployed Cloud Run request logs,
not the source. Neither is visible from code alone: both look like ordinary
call sites until you see how often they actually fire in production. Same
reactive pattern the Process Note calls out - triggered by a "check for
wasteful API calls" ask, not a scheduled sweep.

33. **`/v1/billing/subscription` was in a permanent retry loop - the single busiest endpoint on the service, with a 100% failure rate.** Billing is Phase 3 and unbuilt, so `handlers/unavailable.go` answers 503 by design. But `http_subscription_service.dart` threw on it, `subscriptionStatusProvider` is watched by `ProfilePage` (a keep-alive tab, so it stays mounted), and Riverpod 3 auto-retries a failed provider with backoff - so a permanent, expected 503 became roughly 8-10 requests/minute per device for as long as the app was open. Cost was not the requests (well inside the free tier) but that a request every few seconds stops Cloud Run ever scaling to zero, so a warm instance was billed for the whole session. **DONE (2026-09-10).** `currentStatus()` now maps 503 to the free/none status the backend already synthesizes for a user who has never purchased anything - `isEntitled` stays false, so nothing is unlocked by it. Confirmed live: one call per session (`04:35:56`, `22:00:52`, `22:05:13`) instead of a continuous stream. Also fixed the "Could not load subscription options right now" error on the Premium screen, which was the same 503 surfacing.

34. **Raw GPS coordinates as a Riverpod cache key caused a refetch on every location read.** `openMeetupsProvider` is a `.family` keyed on `(intent, viewerLat, viewerLng, withinDays)`, fed the unrounded device position. Consumer GPS jitters 3-10m even on a stationary phone, so every reading minted a new key, missed the cache, and refetched an identical list. Seen directly in the logs: `/v1/meetups` at latitudes 6.8705648 / 6.8705815 / 6.8705842 / 6.8705933 within minutes from a phone on a desk, and `intent=lunch` fetched twice 21 seconds apart.
