# ADR-011: User-activity analytics and telemetry

## Status

**Accepted. Backend implemented by 29D (working tree, 2026-10-26); the app side is 29E,
the daily report 29F.** See `docs/plans/29D-completion-report.md`.

The decision was recorded, with plan 29A, so
the billing work can leave the right seams (`billing.billing_outbox` already carries
`credits.changed`). Built by plans 29D (backend, OpenTelemetry), 29E (app) and 29F
(daily report). Written 2026-10-24.

## Context

The project needs to know what people use, where they get stuck, which flows they
abandon and what they spend credits on, and it needs this on Cloud Run's free tier
with Supabase's free storage. Nothing is collected today: the app has no analytics,
the monolith's Prometheus metrics are never scraped, and the request id is lost
between the gateway and the monolith.

## Decision

1. **An `analytics` module with its own schema**, the same shape as `billing`: own
   tables, sqlc entry, proto and gRPC server, no cross-schema SQL.
2. **One event envelope** (plan 29 §4.2): device-generated UUIDv7 `event_id` for
   deduplication, `snake_case` event names from an embedded registry that also
   generates the Dart constants, a schema version per event, typed and allowlisted
   attributes (at most 20 keys, strings at most 100 characters, no free text), and
   `user_key = HMAC-SHA256(user_id)` — never the raw id.
3. **Never collected:** names, emails, phones, free text, meetup titles, exact
   coordinates, IP addresses, store receipts.
4. **Ingest is best effort; billing is exactly once.** A bounded in-process buffer
   flushed with `COPY`; when full, events are dropped and counted.
5. **Storage within the free tier:** raw events 14 days in Postgres, day-partitioned,
   archived as gzip NDJSON to the existing Cloud Storage bucket before a partition is
   dropped; daily aggregates kept.
6. **OpenTelemetry** for traces (`otelhttp`, `otelgrpc`, W3C `traceparent` replacing
   the lost request id), metrics (the existing Prometheus registry plus low-
   cardinality business counters) and event logs. Exporters chosen by environment:
   `none` by default, `stdout`, or `otlp`. Moving to Elasticsearch, Grafana or
   BigQuery later is configuration, not code.
7. **Consent:** on by default with an opt-out toggle and a privacy policy update
   (Sri Lanka PDPA No. 9 of 2022), decision D8.
8. **A daily Excel report** generated by the scheduled tick after 06:00 Asia/Colombo
   for the previous day, idempotent by date, emailed and stored.

## Alternatives considered

- **A hosted analytics SDK (Firebase Analytics, Amplitude, Mixpanel).** Quick to add,
  but sends device identifiers and behaviour to a third party, fights the "no PII"
  rule, and the data cannot be joined with credits and meetups. Rejected.
- **An OpenTelemetry SDK in the Flutter app.** No mature mobile Dart SDK is assumed;
  the app sends the envelope and the server converts it.
- **Keeping raw events forever in Postgres.** Exceeds Supabase's free storage within
  months. Rejected for the 14-day window plus archive.

## Consequences

- Analytics can never block or slow a user action: it is fire-and-forget on the
  client and best-effort on the server.
- Account deletion must delete that user's events by `user_key` and remove them from
  per-user aggregates.
- Any new event or attribute needs a registry entry; unknown ones are dropped and
  counted, never stored.
